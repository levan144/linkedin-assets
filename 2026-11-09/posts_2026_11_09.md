## Tue Nov 10, 11:30 — Dev lesson: (int) cast on money

Image: 1-mon-int-cast-money.png

(int) (19.99 * 100) is 1998 in PHP.

Not 1999. Run it.

19.99 can't be stored exactly as a float. Times 100 it's 1998.9999999999998. And (int) doesn't round. It cuts toward zero.

Where it bites: payment APIs. Stripe, for example, wants the amount in the smallest currency unit. 19.99 USD is sent as 1999.

$amount = (int) ($order->total * 100); // 1998

A DECIMAL column doesn't save you here. Eloquent returns it as the string "19.99", and "19.99" * 100 is still 1998 after the cast.

The customer is charged one cent less than the order says. Nobody notices one cent. Then reconciliation shows a batch of orders where the charge never matches the total.

It doesn't happen with every price. 10.99 converts fine. 19.99 doesn't. So tests with a few "nice" prices pass.

The PHP manual says it plainly: never cast an unknown fraction to int.

The fix:
→ Store money as integer cents. Or keep DECIMAL, but never multiply it as a float in PHP.
→ If you must convert: (int) round($total * 100)
→ For tax and discount math: a money library or bcmath, which works on strings.

Where did your last one-cent mismatch come from: floats, rounding, or tax math?

## Wed Nov 11, 11:30 — AI-workflow opinion: AI migrations never saw your data

Image: 3-wed-ai-migration-data.png

AI writes migrations against your schema, not your data.

Ask it to make email unique and add a phone column. You get clean code:

Schema::table('users', function (Blueprint $table) {
    $table->string('phone')->nullable();
    $table->unique('email');
});

It passes locally. Local data is clean.

Now say production has two customers with the same email from an old import. The unique index fails with a duplicate entry error.

On MySQL (unlike Postgres), schema changes aren't transactional. So the phone column is already added, but the migration isn't marked as run. The next deploy tries to add phone again and fails on that too. Now someone is fixing the schema by hand, mid-deploy.

The AI didn't write bad code. It wrote code for data it couldn't see. The reviewer couldn't see it either.

Before any constraint change, I'd:
→ Run the check on a production copy first:
SELECT email, COUNT(*) FROM users WHERE email IS NOT NULL GROUP BY email HAVING COUNT(*) > 1;
→ Keep one risky schema change per migration on MySQL.
→ Give the AI the query results, not only the schema.

What has production data had that your migration didn't expect?

## Thu Nov 12, 11:30 — Dev hot take: SoftDeletes shouldn't be a default

Image: 4-thu-soft-deletes.png

SoftDeletes shouldn't be on every model by default.

It feels safe. Nothing is really gone. But the row is still in the table, and two things still see it.

1. Unique indexes.
A user deletes their account, then signs up again with the same email. Your unique:users,email rule says "already taken". Without the rule, MySQL throws 1062 Duplicate entry.
The index doesn't know about deleted_at. And a unique on (email, deleted_at) doesn't fix it: NULLs never collide.

2. Anything that isn't an Eloquent model query.
Laravel hides soft-deleted rows when you query the model. Not here:
DB::table('orders')->sum('total');
Deleted orders are still in that total. Same for raw SQL, BI tools and CSV exports.

So every unique rule and every report needs a decision about trashed rows. Usually nobody makes it until a number is wrong.

What I'd do instead:
→ Hard delete by default.
→ SoftDeletes only where people need a trash or undo button.
→ For records you must keep (orders, invoices), a status like cancelled. It says what happened. deleted_at doesn't.

Where I'd be wrong: admin panels where restoring deleted records is a weekly job. There the trait pays for itself.

Do you add SoftDeletes by default, or only when someone asks for undo?

## Sat Nov 14, 12:30 — Question: staging data

Text only.

Staging data: production copy or seeded fakes. Both have a catch.

Production copy: real edge cases, real volume. Also real emails and addresses. Skip the scrubbing and one test run can email real customers.

Seeded data: safe and repeatable. But factories never create the duplicate emails and half-filled rows from old imports that break migrations.

The middle option: a production dump where every email becomes user{id}@example.test before anyone touches it.

Which do you use: prod copy, seeded, or the mix?
