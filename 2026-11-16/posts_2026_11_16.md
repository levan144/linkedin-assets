## Mon Nov 16, 11:30 — Dev lesson: month overflow in PHP dates
Image: 1-mon-month-overflow.png

Jan 31 + 1 month = March 3 in PHP.

Run it:

(new DateTime('2026-01-31'))->modify('+1 month');
// 2026-03-03

February has no 31st, so PHP rolls the extra days into March. Carbon's addMonth() overflows the same way by default. So does Laravel's now()->addMonth().

Where it hurts: monthly billing you wrote yourself.

A customer subscribes on Jan 31. Your code sets next_billing_at = addMonth().
→ No February invoice.
→ Next charge on March 3.
→ From then on they renew on the 3rd, not at month end.
→ Your February revenue report is short one customer.

Same bug hides in trial end dates, subscription expiry and "monthly" reports.

The fix:

$start->copy()->addMonthNoOverflow();
// 2026-02-28

Two details that matter:
→ Count from the original start date: $start->copy()->addMonthsNoOverflow($n). Chain from Feb 28 and every later renewal lands on the 28th.
→ Test with Jan 31, Mar 31, Aug 31, and Jan 31, 2028 (leap year: Mar 2, not Mar 3). "Nice" test dates like the 1st or the 15th always pass.

## Wed Nov 18, 11:30 — Freelance opinion: timeline starts on access day
Text only.

A project timeline should start on access day, not signing day.

Illustrative math:
→ 4-week build, contract signed on the 1st.
→ Hosting login arrives on day 6. Payment gateway sandbox on day 12. Real product data on day 17.
→ The deadline still says the 28th.
→ That leaves 11 calendar days (about 8 working days) for everything that needs real data. Or you're "late".

Nobody did anything wrong. Getting access takes time on the client's side: someone has to find the password, ask the old developer, call the hosting company.

What I'd put in the proposal:
→ A short access list: hosting/SSH, admin login, DNS, payment and shipping accounts, API keys, sample data.
→ "The timeline starts when everything on this list is received."
→ Deadlines written as "X working days after access", not a calendar date.
→ With partial access, say in writing which parts you can start now.
→ If something is still missing after X days, you agree a new date together.

It reads less friendly than a fixed date. It's fairer to both sides: the client sees exactly what blocks the start, and you don't absorb their delays for free.

## Thu Nov 19, 11:30 — Dev hot take: database queues are enough for most small apps
Image: 4-thu-database-queue.png

Most small Laravel apps don't need Redis for queues.

New Laravel apps already use the database queue driver by default, and the jobs table migration ships with the skeleton. For a site that sends order emails, syncs stock every few minutes and resizes images, that's plenty.

What you get by staying on the database:
→ One less service to install, secure, monitor and pay for.
→ Pending and stuck jobs are rows you can read with plain SQL.
→ Local, staging and production run the same setup with no extra container.

When I'd switch to Redis:
→ Thousands of jobs per minute, or many workers polling one jobs table.
→ You want Horizon. It only manages Redis queues.
→ Queue queries start showing up next to slow page queries.
→ You already run Redis for cache and sessions anyway.

Where I could be wrong: on cheap shared hosting you may not be able to keep a worker running at all, and a weak MySQL server can feel even modest polling. Check the slow query log before you decide.

## Sat Nov 21, 12:30 — Question: migrations on deploy
Text only.

Migrations on deploy: automatic, by hand, or both.

Automatic: php artisan migrate --force in the deploy script. Every deploy is the same, nobody forgets a step. Add --isolated if several servers deploy at once.

By hand: someone reads the migration first and picks when a slow ALTER TABLE on a big table runs.

Both: review it in the pull request, then let the deploy run it.
