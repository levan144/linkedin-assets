## Mon Nov 2, 11:30 — Dev lesson: env() returns null after config:cache

Image: 1-mon-env-config-cache.png

Add config:cache to a deploy and env() starts returning null.

This runs fine on your laptop:

$key = env('PAYMENT_API_KEY');
Http::withToken($key)->post($url, $payload);

Then someone adds php artisan config:cache to the deploy script. Or php artisan optimize, which runs it too.

From that deploy on, Laravel doesn't load .env. The Laravel docs say env() calls for .env variables now return null.

Every payment request goes out without a valid key. With a payment API, that means failed checkouts, not an error page. The code didn't change. The deploy script did.

The fix:

// config/services.php
'payments' => ['key' => env('PAYMENT_API_KEY')],

// everywhere else
$key = config('services.payments.key');

Rule: env() only inside config/ files. Everywhere else, config().

Two cheap guards:
1. In CI: ! grep -rnE "\benv\(" app/ routes/ (fails the build on a match)
2. Larastan has an opt-in rule: noEnvCallsOutsideOfConfig: true

One twist: if the server sets real environment variables (Docker, some hosts), env() still works there. So it can break on one server and not another.

Where was your stray env() call hiding: a controller, a job, or a package?

## Wed Nov 4, 11:30 — Freelance opinion: real API calls before quoting

Image: 3-wed-api-call-before-quote.png

An API quote made before one real call is a guess.

The docs say REST, JSON, OAuth. It looks like a 20-hour job.

The first real calls, plus one question to their support, show what the docs left out. What I check first:
→ Is there a sandbox, or only production?
→ What's the rate limit? 5,000 products, one request each, at 60 a minute is 83 minutes per full sync.
→ Do dates come with a timezone?
→ Is there pagination, or one huge response?
→ Do webhooks retry if your server is down?

Each "no" adds hours you didn't quote. Illustrative math: a strict rate limit means a queue, retries and progress tracking. 20 hours becomes 30. On a fixed price, that's 50% over, and those 10 hours are yours.

So I split it in two:
1. A small paid first step: get credentials, log in, read one real record, write one test record.
2. Then a fixed quote, based on what actually happened.

If the client can't get you credentials within a week, expect the whole project to move at that speed.

## Thu Nov 5, 11:30 — Dev hot take: repositories in Laravel

Image: 4-thu-repository-pattern.png

Most Laravel repositories are Eloquent with extra steps.

You've seen this:

interface UserRepositoryInterface {
    public function find(int $id): ?User;
}

class EloquentUserRepository implements UserRepositoryInterface {
    public function find(int $id): ?User {
        return User::find($id);
    }
}

Plus a binding in a service provider. Three pieces to call User::find().

The usual reasons:

"We might switch databases." Eloquent already runs on MySQL, MariaDB, PostgreSQL, SQLite and SQL Server. And the repository returns User models, so the rest of the app still depends on Eloquent anyway.

"It's easier to test." Mocking the repository skips the part most likely to break: the query. RefreshDatabase runs it against a real test database, ideally the same engine as production.

What I'd do instead: query scopes for filters you reuse, and one class per big query (like a MonthlySalesReport) when it outgrows a scope.

Where they do make sense:
→ The data comes from an API and a database behind one interface
→ A large team that needs hard boundaries between modules
→ A domain core you want to keep free of the framework

What made you start, or stop, using repositories in Laravel?

## Sat Nov 7, 12:30 — Question post

Text only.

How often do you update dependencies on a live site?

Composer packages or WordPress plugins, same question.

Weekly: small batches, easy to see what broke.
Monthly: fewer deploys, more to test at once.
Security fixes only: least work now, one painful major-version jump later.

I lean weekly: composer.lock in git, tests, plugins updated on staging first. composer outdated --direct shows what's waiting.

What's your rule: weekly, monthly, or security fixes only?
