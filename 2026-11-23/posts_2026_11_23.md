## Mon Nov 23, 11:30 — Dev lesson: array_filter() keeps keys, JSON becomes an object
Image: 1-mon-array-filter-json.png

array_filter() can turn your JSON array into an object.

Run it:

$ids = [12, 0, 31, null, 47];
echo json_encode(array_filter($ids));
// {"0":12,"2":31,"4":47}

array_filter() keeps the original keys. Keys 1 and 3 are gone, the array is no longer a list, so json_encode() writes an object.

Laravel collections do the same when you return ->filter() directly. (API Resource collections re-index for you.)

The fix is one call:

array_values(array_filter($ids)); // [12,31,47]
$products->filter()->values();

Why it slips through: it only breaks when an item before the last one gets removed. Tests with clean data pass. Then one product in the middle goes out of stock, the endpoint returns an object, and the frontend's .map() throws. That's how one product can blank a whole list.

Bonus: with no callback, array_filter() also drops 0, "0" and "". A price of 0 disappears too.

Which PHP function surprised you by keeping (or dropping) keys?

## Wed Nov 25, 11:30 — AI-workflow opinion: check AI-suggested packages before composer require
Text only.

AI suggested a Composer package? Check Packagist before installing.

AI coding tools sometimes invent package names that sound right.

A USENIX Security 2025 paper tested 16 code models on 576,000 Python and JavaScript samples. On average, at least 5.2% of packages suggested by commercial models didn't exist. For open-source models: 21.7%. Over 205,000 unique fake names.

A name a model keeps inventing is a name an attacker can register.

The study didn't cover PHP. Vendor namespaces help: nobody else can publish under spatie/. But an invented vendor name is open to anyone. And a package's autoload files can run on every request, next to your .env, database and customer data.

My 30-second check:
- Packagist page exists and links to a real repository
- downloads and release history make sense for its age
- the vendor is who you think it is

If it fails any of these, I find the real package or write the code myself.

## Thu Nov 26, 11:30 — News + hot take: PHP 8.6 session defaults
Image: 4-thu-php86-sessions.png

PHP 8.6 is out. Check your sessions before you upgrade.

It shipped on Nov 19 (php.net). The new functions get the attention. The change I'd test first is quieter: an accepted RFC flips three session defaults.

session.use_strict_mode: 0 → 1
session.cookie_httponly: 0 → 1
session.cookie_samesite: "" → Lax

Good defaults. If your code calls session_start() and nothing overrides them:
- JavaScript can no longer read the session cookie
- the cookie isn't sent on cross-site POSTs, like some payment return pages
- a session ID that isn't already in storage gets replaced with a new one

An old php.ini or an ini_set() in code can keep the old values. Check what you actually run: php -i | grep session

Laravel and WordPress core don't use PHP's native sessions. The risk is custom PHP apps and plugins that call session_start().

Worst case: a customer pays, comes back from the gateway, and the session is gone.

My rule: tests on 8.6 this week, plus one real checkout on staging in Firefox and Safari. Production after the first patch release.
Where I'd be wrong: an app with good browser tests can move in week one.

Do you upgrade PHP in week one, or wait for the .1?
