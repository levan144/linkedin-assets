## Mon Oct 26, 11:30 — Dev lesson: dispatching a job inside a DB transaction

Image: 1-mon-job-inside-transaction.png

Your queued job can run before the order exists.

This looks safe:

DB::transaction(function () use ($data) {
    $order = Order::create($data);
    SendReceipt::dispatch($order);
    $this->reserveStock($order);
});

With a Redis or SQS queue, the job leaves right away. The transaction hasn't committed yet.

Two ways it goes wrong:

1. A fast worker picks it up before the commit. The order isn't in the database yet, so the job throws ModelNotFoundException. A missing model fails the job right away, retries or not. The order shows up a second later. The receipt never goes out.

2. reserveStock() throws and everything rolls back. The job is already in the queue, for an order that never existed.

The fix is one call:

SendReceipt::dispatch($order)->afterCommit();

Now the job waits for the commit, and it's thrown away if the transaction rolls back.

Or set 'after_commit' => true on the queue connection. It's false in Laravel's default config, and it also covers queued listeners, queued mail and notifications.

(If your queue uses the database driver on the same connection, the job row is part of the transaction, so you're mostly safe. Redis and SQS aren't.)

Has a job ever run before its commit on you, and what gave it away?

## Wed Oct 28, 11:30 — AI workflow opinion: AI-written tests lock in bugs

Image: 3-wed-ai-tests-expected-values.png

Let AI write tests. Never let it pick expected values.

Here's the trap.

The spec says 20% VAT. The code has a typo:

return $cents + intdiv($cents * 18, 100);

Ask an AI to "write tests for this function", give it only the code, and you get:

assertSame(11800, totalWithVat(10000));

Green. Coverage goes up. The bug now has a test protecting it.

Illustrative math: 10,000 invoices of €100, each €2 short. That's €20,000 of VAT nobody charged.

A test written by reading the code only proves the code does what it does.

The split I'd use:
→ The expected numbers come from a person: the spec, a real invoice, the client's spreadsheet.
→ AI writes the setup, the factories and the list of edge cases to check.
→ The prompt: "Here are the expected values from the spec. Write tests that assert them."

Typing 11800 vs 12000 by hand takes ten seconds. It's the part of the test that matters most.

Do you type expected values by hand, or let AI fill them in?

## Thu Oct 29, 11:30 — News + lesson: the Oct 21 PHP security release

Image: 4-thu-php-patch-check.png

PHP's Oct 21 fix: three places the old version survives.

On Oct 21, PHP released fixes for two critical bugs, CVE-2026-109618 and CVE-2026-109619. php.net says they can allow unauthenticated remote code execution. Both are rated 9.2 (CVSS v4).

Fixed in 8.5.12, 8.4.27, 8.3.36 and 8.2.35. PHP 8.1 and older get no new release from php.net: use a vendor backport or upgrade.

What I'd check on every server, based on the php.net advisory and the Laravel Forge docs:

1. Auto-updates. If PHP comes from a third-party repo like the ondrej/php PPA, Ubuntu's unattended upgrades won't patch it by default. Forge says its own automatic updates don't patch PHP either.

2. FPM, not just the CLI. php -v shows the CLI. Check php-fpm8.4 -v (your version), and make sure the FPM service actually restarted. On mod_php, restart Apache.

3. Long-running processes. Queue workers, Horizon, Octane and Reverb keep running the old PHP until you restart them.

"We have auto-updates" can be the wrong answer here. If you look after client servers, check each one and every installed PHP version, not just the one the site uses.

Which one would have caught you: auto-updates, FPM or workers?
